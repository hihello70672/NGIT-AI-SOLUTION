## Integration gates

1. **Inspect and reconcile:** preserve implementation; inspect actual API routes/schemas, modules, frontend conventions, migration inventory and shared contracts. Reconcile from repository contents before changes.
2. **Stabilize shared contracts:** Chief Architect reviews boundary/dependency changes. Document typed contracts, server caller context, ownership, persistence, failure behavior and test expectations.
3. **Foundation/security:** apply ordered migrations on fresh PostgreSQL 16+; provision intended non-owner/non-superuser application role; verify grants, RLS and cross-user isolation without `BYPASSRLS`; integrate trusted transaction-local identity. Verify Compose startup/shutdown.
4. **Integrate by dependencies:** complete phases 1–2, then 3–4, 5–7, 8–9, 10–11, and finally 12. Later modules may not bypass identity, ownership, security, audit or contracts.
5. **Honor operational limits:** one API worker while approval/security/task state is process-local. Filesystem path checks are not OS sandboxing. Browser requires SSRF/network protections; computer-control requires an explicitly constrained injected adapter.
6. **Run and report:** run API/web suites, database/RLS checks, Compose lifecycle, frontend build and applicable end-to-end startup. Record exact commands, environment and outcomes. Create `docs/TEST_REPORT.md` only after tests actually execute; no passing claims from source inspection.
7. **Release gate:** downloadable ZIP, release/tag and verified-installation claims require phase-12 evidence. None is implied by this plan.

Open decisions remain those in [Architecture §6](ARCHITECTURE.md#6-decisions): migration/ORM evolution, auth/session/token, durable security/task state, grants/RLS strategy, vector/embedding persistence, model runtime packaging, WebSocket semantics, media storage, payment/provider/secret design, event transport, production topology/operations and API naming/error conventions.
